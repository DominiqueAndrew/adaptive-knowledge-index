# Next research test: task benefit against strong fresh caches

This is a design amendment, not an executed experiment or a new resource
authorization. Runtime validation is blocked as described in
[the root-cause audit](RUNTIME_ROOT_CAUSE_AUDIT.md). Preserve the frozen 24-task,
six-repository cohort and the uninspected 12-task held-out split. Do not replace
legacy tasks because they are difficult to provision or inspect held-out actions
to choose an attractive candidate. The earlier task-420 pilot would establish
instrumentation feasibility only, not repair success or an AKI advantage.

## Evidence-driven scope

The [phase-two experiment](PHASE2_RESULTS.md) found that even free reuse of every
valid repeated closure saved at most 0.339% on the task-derived history workloads.
Frequency admission was the strongest simple demand cache by mean lifecycle cost;
disabled adaptation was faster on some real histories. The incremental-maintenance
gain was common to all policies, not evidence for a new optimizer. The observed
agent prefixes were too short and incompletely timed to establish a new reusable
operation. Consequently no further closure-admission tuning is justified.

The next candidate must come from **measured prospective operations**, with source
states and timings recorded before and after every operation. Measure safe shared
work beyond exact-query caching, such as repeated parsing, candidate generation or
evidence packaging only if it actually occurs. Do not insert expensive processing,
target-generated warm-ups or artificial repetition to make reuse win. Count
observer, dispatch, model and maintenance costs; a fast query is insufficient if
the agent's overall attempt remains unchanged.

## Stage A: falsify opportunity before implementation

After runtime acceptance, use only the already-designated development tasks and
approved model/tool configuration. Keep all attempts, including failures and cap
exhaustion. A short 12-operation pilot cannot estimate resolved-task rates.

For each candidate operation, report exact/version-valid repeated work, changed
dependencies, opportunity beyond an exact result cache, and its fraction of full
attempt cost. Run the optimistic free/unlimited-cache diagnostic separately; label
it an upper bound. If it cannot plausibly reach the existing 20% lifecycle target,
stop that candidate. This is a stop rule, not a reason to select tasks with more
reuse. With the current evidence, incremental evidence maintenance remains the
useful deliverable and adaptive selection remains unproved.

## Stage B: freeze a matched comparison

Before held-out execution, select the strongest simple policy on development
measurements only: include disabled reuse, exact versioned result caching, frequency,
LRU and GDS-style retention. Give each the same incremental source maintenance,
artifact family, source access, freshness checks, storage cap, token budget and
durability policy. Include bounded static materialization; label unbounded static
as a reference, never a matched-budget competitor. A cache may reuse only current
source evidence. Gold paths, solutions, test outcomes and future queries must not
enter admission or policy state.

Freeze one winning baseline and one AKI candidate, model/scaffold revision,
prompt/tool definitions, supported languages, budgets, mutation protocol and seeds
before opening held-out tasks. Randomize paired condition order and run serially
in the exclusive runtime. Keep adaptation state within its declared chronological
repository stream. Reset cold-start trials; separately report legitimate warm reuse,
unseen tasks, source changes and drift. Evaluation code must prevent cross-condition
artifact sharing and future-source access. Deterministic replay and new agent runs
answer different questions and must remain separate.

## Primary outcome is an actual attempted task

Use the reviewed task's executable test protocol for resolution, with a fixed
model/scaffold/tool/wall budget per attempt. Record test availability and protocol
deviations; missing tests do not count as success. Compare paired resolved outcomes,
full cost per attempted task, cost per resolved task, wall latency, source freshness,
abstention and evidence exposure under the token budget. Report runtime setup and
teardown separately and amortize them only under an explicit deployment model.
Provide model tokens and observed CPU/wall cost separately; do not invent dollars
for subscription usage. Count no-answer and failed attempts in denominators.

A defensible practical gain requires lower total task cost than the frozen strongest
baseline **and** a predeclared quality noninferiority criterion. Freeze the margin
and powered sample-size plan using development evidence before held-out evaluation.
The current 12-task held-out split can provide feasibility/paired descriptive data;
do not declare a general noninferiority result from an insignificant difference on
that small sample. Additional tasks would need an outcome-blind cohort extension
registered before inspection, not post-hoc selection to recover a headline.

Use repository-clustered uncertainty, per-task-family/repository results and all
paired outcomes. Any stale evidence presented as current is a failure even if the
agent eventually passes tests. Report observer overhead, p50/p95 and lifecycle
break-even only with enough genuine measurements. A single successful repair, a
synthetic cache win, common maintenance savings or replay speedup is not an agent
breakthrough. If strong caches match AKI or task benefit disappears, publish that
negative result and retain the narrower incremental-maintenance tool.

Resource requests follow measured need: first resolve runtime/accounting readiness;
then quote one development instrumentation pilot with explicit CPU/disk/tool/model
caps. Only accepted development traces can justify the larger paired task study.
No live operation or model call is enabled by this document.
